# コンテンツ出典・ファクトチェック運用

## 目的

雑学クイズと知識カードについて、出典を特定可能な形で記録し、公開前に人が確認した証跡を残します。

`sourceNote`は既存データとの互換性のため残します。新規追加・更新するコンテンツでは、必ず`source`オブジェクトも設定してください。

## JSON形式

```json
{
  "sourceNote": "気象庁",
  "source": {
    "title": "資料またはページの正式名称",
    "publisher": "発行元・運営元",
    "url": "https://example.go.jp/source",
    "verifiedAt": "2026-07-12",
    "verificationLevel": "primary",
    "reviewStatus": "approved"
  }
}
```

### verificationLevel

- `primary`: 官公庁、公式統計、法令、規格、原著論文、公式資料
- `secondary`: 信頼できる報道、専門誌、学術的な二次資料、百科事典
- `unverified`: 原典または十分な二次資料を確認できていない

### reviewStatus

- `approved`: 人が本文と出典を照合し、公開可能と判断した
- `pending`: 確認中
- `rejected`: 誤り、根拠不足、表現上の問題などにより公開不可
- `legacy`: 旧形式の`sourceNote`だけを利用している

`approved`にするには、`title`、`publisher`、HTTP(S)の`url`、`verifiedAt`、`primary`または`secondary`の`verificationLevel`が必要です。

## 監査コマンド

通常の開発・CIでは、構造化情報が未設定の項目を「要確認」としてレポートに出します。未設定だけでは既存開発を止めませんが、壊れたURLや不完全な`approved`情報は失敗になります。

```bash
dart run tool/audit_content_sources.dart
```

出力先:

```text
build/reports/content_source_audit.md
```

一般公開判定では、全件承認済みを必須にします。

```bash
dart run tool/audit_content_sources.dart --require-approved
```

## レビュー手順

1. 問題文、選択肢、正答、解説、カード本文を確認する。
2. 原則として一次資料を探す。一次資料が難しい場合は信頼できる二次資料を使う。
3. 出典ページが記述内容を直接裏付けているか確認する。
4. 数値、制度、ランキングなど変化しやすい情報は確認日を特に重視する。
5. 問題と関連カードが同じ根拠に基づく場合は、同じ出典URLを設定する。
6. 確認者が`reviewStatus`を`approved`へ変更する。
7. `--require-approved`を実行し、監査結果が0件になることを確認する。

## 禁止事項

- 検索結果の要約だけを根拠にする
- 出典を確認せず`approved`へ変更する
- 「Wikipedia」「○○省」など、資料を特定できない名称だけで承認する
- AI生成文を一次資料として扱う
- 医療、法律、投資などの専門的助言に見える表現を、十分な根拠なしに掲載する

## 現行データの扱い

旧データは`sourceNote`から読み込めるため、アプリは引き続き動作します。ただし監査上は`legacy`として「要確認」になります。全件の人手確認が終わるまでは、一般公開のリリースゲートを通過したとはみなしません。
